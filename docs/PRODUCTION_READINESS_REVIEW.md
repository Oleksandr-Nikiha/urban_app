## 🧑‍💼 Захід 2: Робота менеджера та персоналу закладу (POS, каса, столи, замовлення)

### 🌟 Що вже реалізовано на відмінно:
- **PIN-авторизація з безпечним хешуванням (`PinLockScreen`):** Швидке перемикання між офіціантами/барменами за 4-значним кодом, захист від підбору (rate-limiting у Redis) та хешоване збереження пінів у БД.
- **Повноцінний касовий цикл змін (`ShiftModal`):** Відкриття зміни з фіксацією розмінної монети, службові внесення готівки, службові вилучення (інкасація) та закриття зміни зі звіркою залишку в скриньці.
- **Швидкий калькулятор готівки та решти (`PaymentModal`):** Пресети банкнот (100, 200, 500, 1000 грн) та миттєвий розрахунок решти запобігають помилкам касира.
- **Гнучке керування столами та дозамовлення:** Можливість додавати нові позиції до вже відкритого замовлення (`POST /orders/{id}/items`), маркування страв як виданих (`toggle-served`).
- **Моментальний пошук та реєстрація клієнта за номером:** Інтеграція програми лояльності прямо в екран розрахунку: касир вводить номер, бачить бонусний баланс і списує бонуси в один тап.

### ⚠️ Точки росту для продакшену (Операційні ризики HoReCa):
1. **Фіскалізація через ПРРО (Checkbox / Вчасно.Каса / Cashalot):**
   - *Критичність: ВИСОКА (Юридична та податкова вимога в Україні).*
   - *Потреба:* Без автоматичної фіскалізації при закритті чека заклад не зможе легально працювати. Необхідно додати модуль надсилання чека в ПРРО при `close-table`.
2. **Друк зустрічних чеків (кухонних бігунків) та пречеків:**
   - *Потреба:* Кухарям на гарячому/холодному процесі та бармену потрібен автоматичний друк тікетів на термопринтер (ESC/POS 80мм) при натисканні «Відправити на кухню».
3. **Розділення рахунку (Split Bill) та змішана оплата:**
   - *Ситуація:* Компанія за одним столом просить розрахувати кожного окремо, або гість платить 200 грн готівкою, а решту карткою. Зараз чек закривається однією транзакцією.
4. **Управління Стоп-листом (Stop-list) в один клік:**
   - *Потреба:* Можливість для старшого зміни в 1 тап позначити страву чи десерт як недоступний, з миттєвою синхронізацією в клієнтський Telegram Mini App.
5. **Менеджерський PIN для скасувань та великих знижок:**
   - *Захист від крадіжок:* Скасування замовлення (`CancelOrderModal`) або знижка >15% повинні вимагати підтвердження піном адміністратора, а не будь-якого офіціанта.

- **Ізоляція та безпечні контейнери:** Всі сервіси загорнуті в Docker Compose, бекенд та Redis мають вбудовані `healthcheck`, діє політика `restart: unless-stopped`.

### ⚠️ Точки росту для адміністратора до релізу:
1. **Автоматизація щоденних бекапів (Disaster Recovery):**
   - *Проблема:* Скрипт `backup_prod_db.sh` створено, але він **не доданий до cron / systemd.timer**. Наразі бекапи бази робляться лише вручну.
   - *Рішення:* Додати таймер або завдання в cron (щоночі о 03:00) та налаштувати відправку бекапів за межі сервера (S3 / Cloudflare R2 або Telegram-канал бекапів).
2. **Перехід з DuckDNS на постійний комерційний домен:**
   - *Проблема:* Зараз публічний доступ працює через `nikiga-ax.duckdns.org`.
   - *Вимога:* Для публічного ресторану потрібен брендовий домен (`.ua` або `.com.ua`). Це критично для проходження офіційної верифікації Telegram Bot WebApp, сертифікації платіжних систем (Monobank/LiqPay) та довіри користувачів.
3. **Ротація логів Docker (Log Rotation Policy):**
   - *Ризик:* За замовчуванням логи контейнерів (`json-file`) можуть розростатися до десятків гігабайтів і переповнити системний диск.
   - *Рішення:* Прописати ліміти логів у `docker-compose.yml` (`max-size: "50m"`, `max-file: "5"`).
4. **Моніторинг збоїв та алертинг (500 Error Alerts):**
   - *Потреба:* Якщо у клієнта впаде чекаут чи API видасть 500 помилку, адміністратор повинен миттєво отримати повідомлення в Telegram (через бота адміна або Sentry).
5. **Актуалізація цифр у документації:**
   - *Нюанс:* У `README.md` все ще зазначено 178 тестів замість актуальних 190, та міграція 0026 замість 0027. Потрібна легка косметична синхронізація.

## 💻 Захід 4: Розробник (Якість коду, архітектура, швидкодія, тести)


### 🌟 Що вже реалізовано на відмінно:
- **Високопродуктивний асинхронний стек:** Пряме використання `asyncpg.create_pool` (без важкого ORM оверхеду) з лімітами з'єднань (`min_size=2`, `max_size=20`, таймаути 10-15с).
- **Розумне дворівневе кешування з автоінвалідацією:** Кешування каталогу в Redis з підпискою на PostgreSQL `pg_notify ('catalog_cache_invalidate')` — при зміні страв кеш скидається автоматично у фоні.
- **Fail-Safe підключення до Redis:** Якщо Redis тимчасово недоступний, API не падає, а плавно переходить у режим прямого запиту (fallback) без простою сервісу.
- **Централізований пакет спільних контрактів (`web-shared`):** Єдине джерело істини для типів TypeScript, моделей та API-клієнтів між усіма 6 додатками.
- **Швидкісний набір автотестів:** 190 асинхронних тестів виконуються всього за 10 секунд (100% green).

## 🛡 Захід 5: Повний аудит безпеки (Security Audit)

### 🌟 Що вже реалізовано на рівні кращих безпекових практик:
- **Криптографічна валідація Telegram InitData:** Повна перевірка HMAC-SHA256 підпису на основі секретного ключа бота. Захист від підробок та перевірка часу життя сесії `auth_date` (захист від replay-атак).
- **Імунітет до SQL-ін'єкцій та XSS:** 100% запитів у БД використовують строго типізовані параметри `$1, $2` через asyncpg. На фронтенді повністю відсутній `dangerouslySetInnerHTML`.
- **Захист від IDOR (Insecure Direct Object Reference):**
  - Замовлення в Telegram Mini App фільтруються за `telegram_id` поточного користувача.
  - Веб-замовлення захищені підписаними HMAC `tracking_token` — зловмисник не може перебирати ID і читати чужі телефони та адреси.
- **Безпечна обробка завантаження файлів (File Upload Defense):** Білий список дозволених типів, випадкові 16-hex UUID імена, а головне — обов'язкове перекодування растрових зображень у WebP через Pillow, що гарантовано знищує шкідливий код, поліглоти та EXIF-ін'єкції.
- **Мережева ізоляція бази даних:** Порти PostgreSQL та Redis взагалі не опубліковані назовні та доступні лише всередині ізольованої Docker-мережі.

### ⚠️ Виявлені мінорні вразливості та заходи зміцнення (Hardening):
1. **Відкритий Swagger UI та OpenAPI Schema у продакшені:**
   - *Ризик (Low/Medium):* Ендпоінти `/api/docs`, `/docs` та `/api/openapi.json` публічно доступні. Схема розкриває внутрішню структуру API, DTO та параметри для зловмисників.
   - *Рішення:* Вимикати Swagger або закривати його за staff-авторизацією, якщо `ENV=production`.
2. **Відсутність HSTS у Caddyfile:**
   - *Ризик (Low):* У Caddy налаштовані CSP та nosniff, але відсутній заголовок `Strict-Transport-Security "max-age=31536000; includeSubDomains; preload"`.
   - *Рішення:* Додати HSTS-заголовок у блок публічного хоста.
3. **Гранулярний Rate Limiting для чутливих точок:**
   - *Рекомендація:* Для ендпоінтів перевірки PIN-коду POS (`/api/pos/auth/pin`) та телефонного входу встановити жорсткіший ліміт (макс. 5 спроб за 5 хвилин для одного IP/номера) на додачу до загального лімітера.
4. **Захист Cookie у веб-вітринах:**
   - Переконатися, що всі токени, збережені у Cookie клієнта, мають обов'язкові прапорці `SameSite=Lax` та `Secure` (передача виключно через HTTPS).
